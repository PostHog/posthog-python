Send `$experiment_exposure` for config version 2 experiment splits, and add rule attribution to `$feature_flag_called` for config version 2 flags. A read that sends `$feature_flag_called` now also sends `$experiment_exposure` when the flag was evaluated remotely and its config version 2 record is a complete experiment split: reason code `experiment_split`, rule type `experiment`, a rule ID and a variant key. This applies to `get_feature_flag()`, `feature_enabled()`, `get_feature_flag_result()`, and the `is_enabled()` and `get_flag()` reads of an `evaluate_flags()` snapshot. The exposure carries `$feature_flag`, the same `$feature_flag_response` as its `$feature_flag_called`, `$feature_flag_variant`, `$feature_flag_rule_id` and `locally_evaluated: false`, plus the flag ID, flag version, request ID and evaluation time when the response has them. It does not carry the config version, reason code or rule type, which stay on `$feature_flag_called`. Minimal-event mode does not apply to the exposure. The SDK sends one exposure per distinct ID, groups, flag, rule and variant. The value, request ID and evaluation time are not part of this dedupe, a flags reload does not reset it, and it is separate from the `$feature_flag_called` dedupe. No other outcome sends an exposure: not a targeting match, rollout miss, paused experiment, holdout or failed record, and not a config version 1 flag, a flag from a server without typed values or a locally evaluated flag. A config version 2 `$feature_flag_called` carries `$feature_flag_config_version` 2 and `$feature_flag_reason_code`, which replaces `$feature_flag_reason`. A complete experiment split also adds `$feature_flag_rule_id`, `$feature_flag_rule_type` and `$feature_flag_variant`. A targeting match (rule type `targeted_release` or `percentage_rollout`), a rollout miss (`percentage_rollout` or `experiment`), a paused experiment or a holdout (`experiment`) adds `$feature_flag_rule_id` and `$feature_flag_rule_type`. Other reasons and failed records add no rule properties. The rule ID and rule type are sent as a pair or not at all: when a record has only one of them, a rule type its reason does not allow, or a rule ID that is not a hyphenated UUID, the event drops both and keeps the config version and reason code. A split that is missing its rule type, rule ID or variant key sends no exposure and no rule properties. A reason code the SDK does not know is sent unchanged with no rule properties, and a record without a reason code still sends its config version. None of this changes the value a read returns. The `$feature_flag_called` dedupe of a config version 2 flag includes its attribution, so equal-valued arms, successive experiments of one flag and a holdout after a variant are each reported. Minimal `$feature_flag_called` events keep the attribution. The SDK tries the two events separately. If capture of one raises or drops it (a full or closed queue, opt-out or a disabled client), the other is still sent, and the failed event keeps no dedupe entry, so a later read tries it again. An event that `before_send` drops counts as handled: it keeps its dedupe entry, and later reads do not offer it again. `get_feature_flag_payload()` sends no flag events by default; a call with `match_value` reports the caller's value, so it sends no exposure. `send_feature_flag_events=False` suppresses both events. Events of config version 1 flags, flags from servers without typed values and locally evaluated flags do not change, including their `$feature_flag_reason`, and `$feature_flag_response` does not change on any event.
